# Spike 結論

> 狀態：測過一段 `say` 合成語音、一段 5 分鐘收外放演講的錄音，以及**一段照稿念的真人錄音（有正確答案，字錯率可信）**。

## 環境

- macOS 27.0.1、Apple Silicon、只裝了 Command Line Tools（沒有 Xcode）
- SpeechTranscriber 支援 `zh_TW`（模型已預先安裝）
- AFM 可用、支援 zh-TW，context window 8192 tokens

## 可行性

| 項目 | 結果 |
|---|---|
| 沒有 Xcode 能不能編 SpeechAnalyzer + AFM | ✅ `swiftc` 加上 CLT 的 SDK 就能編 |
| 轉錄錄音檔 | ✅ |
| 錄麥克風、邊錄邊出字、存成 m4a 和 md | ✅ 5 分鐘一次錄完，暫定結果大約每 15 秒確定成一段 |
| AFM 整理和摘要 | ✅ 一次要求大約 6 秒 |

## 合成語音測試（say-test，23 秒，中英夾雜）

| 引擎 | CER | 耗時 | 速度（倍即時） |
|---|---|---|---|
| SpeechAnalyzer (zh_TW) | 12.1% | 0.6 秒 | 約 40 倍 |
| whisper.cpp large-v3-turbo | 5.2% | 7.9 秒（含載入模型） | 約 3 倍 |
| SpeechAnalyzer + AFM 整理 | 12.1% | 另加約 6 秒 | — |

觀察：
- **SpeechAnalyzer 辨識英文術語很差**：Hyperf → hepert、staging → slanging、MR → Mirer、callback log → calebacklod。中文部分大致正確，但沒有標點。
- **whisper 的術語辨識好很多**，而且會自動加標點，但會把英文大小寫改掉（HIPERF、Mr.），還出現了「下周」這種用字。
- **AFM 整理只補了標點、分了段**，沒有修正任何辨識錯的術語，CER 沒有改善。摘要的條列可以讀，但會照抄錯字。

## 真人錄音測試（2026-10-14_1332，5 分鐘，用麥克風收外放的演講）

內容是在講 AI 時代的工程師、code review、心流。是從喇叭外放再由 MacBook 麥克風收音，音質比直接講話差。

| 引擎 | 耗時 | 可讀性 |
|---|---|---|
| SpeechAnalyzer（即時） | 錄完幾乎馬上出結果 | 差，只能抓到大意，很多句子不通順 |
| whisper.cpp large-v3-turbo | 25 秒（約 12 倍即時） | 明顯較好，大部分句子讀得懂，還有標點 |
| AFM 整理（接在 SpeechAnalyzer 之後） | 33 秒 | 只加了標點，內容沒有改善 |

具體差異：

| 原意 | SpeechAnalyzer | whisper.cpp |
|---|---|---|
| 心流 | 心理 / 新靈 | 新流 / 心理 |
| 第一性原理 | 冰性原因 / 一性原因 / 第星人 | 第一性原理 ✅ |
| 千萬不要看 code | 韆萬不要看客 | 千萬不要看扣 |
| code review | col revie / 科戶 rbi | co-review |
| 丟給 AI | 給 AA 丟給 AAG | 丟給AI ✅ |
| 可觀測性 | 可恭敬看得見 | 可觀性，看得見 |

其他發現：
- **SpeechAnalyzer 的 zh_TW 會出現繁簡轉換錯字**：迴來、裏麵、韆萬、家裏。看起來是先辨識成簡體再轉繁體，一字對多字的地方轉錯了。AFM 會修掉一部分（迴→回、韆→千）。
- **AFM 摘要會編造內容**：兩次測試都在「待辦事項」底下列出原文沒有的東西（「釐清誰負責睡眠問題」）。prompt 要改成只摘錄原文明確說過的內容，沒有待辦事項就不要列。
- **AFM 沒辦法把錯字修好**：辨識錯得太嚴重時，它只會照原樣加標點。所以 AFM 不能用來彌補辨識引擎的弱點。

### AFM 接在 whisper 之後（修正 prompt 後）

prompt 改成：整理時用全形標點，只修有把握的錯字；摘要只能用原文的資訊，只有明確交代的事情才列待辦。

- 整理（31.7 秒）：改成全形標點、分成 5 段，錯字幾乎沒改（扣、新流、闖出都還在）。只有一處「馬克思考」被改成「馬斯克思考」，算是猜的。
- 摘要：比接在 SpeechAnalyzer 後面好很多，「code review 五點」的結構完整抓出來了，沒有再出現「睡眠問題」那種編造。
- 但**還是列了「待辦事項」**，把演講裡「你應該…」的建議當成待辦。只靠 prompt 擋不住，正式做的時候可以考慮讓使用者選要不要列待辦，或用 Generable 結構化輸出，讓「待辦」變成可以是空的欄位。

### 摘要改用結構化輸出（DynamicGenerationSchema）

- **CLT 沒辦法用 `@Generable` 巨集**：巨集的實作（FoundationModelsMacros）只有 Xcode 才有。改用執行時建立的 `DynamicGenerationSchema`，效果一樣。正式開發用 Xcode 時可以換回 `@Generable`。
- schema 有三個欄位：`kind`（meeting / talk / memo / other）、`keyPoints`（1 到 8 項，每項不超過 30 字）、`actionItems`（只放會議中明確指派的工作或決議，可以是空的）。
- 結果：判斷為 `talk`，**`actionItems` 是空的，待辦事項的問題解決了**。
- 第一版沒有限制 `keyPoints` 的長度，結果模型把逐字稿逐句抄進去。加上最多 8 項、每項不超過 30 字之後，摘要變成 5 項。
- 新問題：5 項重點都集中在「心流」和「職涯」，**漏掉了演講主軸「code review 要理解的五點」**。8 項的上限可能太緊，或模型比較偏重後半段內容，還要再調。

### 摘要改成兩層：主題 → 要點

- `topics` 最多 6 個主題，每個主題有標題（不超過 15 字）和 1 到 5 個要點（每點不超過 30 字），並要求「依講述順序、涵蓋開頭到結尾」。
- 結果：分成 6 個主題，**「code review 要理解的五點」完整列出來了**，前半段和後半段都有涵蓋。耗時 33 秒。
- 小問題：「提問與第一性原理」被排到最後，但在原文裡它出現在「心流」之前，沒有完全照講述順序。
- 辨識錯字會跟著帶進摘要（扣、新流、理念、馬克思講的），摘要品質的上限取決於逐字稿的品質。

## Breeze ASR 25 對照（同一段 5 分鐘錄音）

用 `ggml-breeze-asr-25-f16.bin`（約 3 GB，whisper-large-v2 微調版）。耗時 55 秒（約 5.4 倍即時），比 turbo 的 25 秒慢一倍。

| 原意 | large-v3-turbo | Breeze ASR 25 |
|---|---|---|
| code / code review | 扣 / co-review | **code / code review** ✅ |
| debug | 抵Bug | **debug** ✅ |
| 偷懶 | 偷懷 | **偷懶** ✅ |
| 這個程式接下來的行為 | 這個層次接下來的行為 | **這個程式接下來的行為** ✅ |
| 同時負責三件事情 | 同時負責穿越思綠 | **同時負責三件事情** ✅ |
| 工程設計者 | 公設設計者 | **工程設計者** ✅ |
| 第一性原理 | **第一性原理** ✅ | 低音系的原因 ❌ |
| 丟給 AI | **丟給AI** ✅ | duplicate image ❌（幻覺） |
| 心流 | 新流 / 心理 | 心理 / 心裡 |

- **Breeze 對英文術語和台灣口語明顯比較強**（code、debug、output、rename 都抓對了），整體可讀性也比 turbo 好。
- 但有幾處**比 turbo 差**：「第一性原理」沒抓到，「丟給 AI」變成完全無關的「duplicate image」（whisper 系列典型的幻覺）。
- **沒有標點**，輸出是一行一個短句；如果要用，需要靠 AFM 補標點。
- 兩個模型錯的地方不太重疊。正式做的時候可以考慮讓使用者選模型，或預設用 Breeze、再用 turbo 交叉比對。

### AFM 接在 Breeze 之後

結果在 `recordings/2026-10-14_1332.breeze.md`，AFM 耗時 29.5 秒。

- **整理**：標點補得不錯，但**分段失敗**，126 個短句幾乎全部接成同一個大段落。turbo 版有分成 5 段。可能是 Breeze 一行一短句的輸出讓模型抓不到段落邊界，可以考慮先把短句合併成約 30 秒一段，再交給 AFM。
- **摘要**：6 個主題，code review 五點也都有，英文術語比 turbo 版正確（code、code review）。
- **但辨識錯誤會變成摘要裡的「事實」**：「duplicate image」變成「年輕工程師從複製圖片開始協調工作」，「低音系」也照抄。逐字稿裡的錯字讀者還看得出來，進了摘要就很難分辨真假，這是比錯字更大的風險。

## Claude Haiku 5.5 取代 AFM（雲端，只送逐字稿文字）

`haiku.py`，一次呼叫，用 JSON schema 結構化輸出：整理後全文（修正處標成「正確〔原：原文〕」，不確定的標〔?〕）、修正紀錄、兩層摘要。輸入是 Breeze 的逐字稿。

- 耗時 29.6 秒（含 adaptive thinking，effort medium），輸入 3.4K / 輸出 7.2K tokens，**約 US$0.004**。速度和 AFM 差不多，沒有比較快。
- **修正錯字明顯比 AFM 強**：「心理/心裡 → 心流」全文都改對了，「多功能 → 多工」也對。AFM 一處都沒改。
- **幻覺有被擋下來**：「duplicate image」標成〔?〕，沒有寫進摘要。AFM 把它寫成了「從複製圖片開始協調工作」。
- 段落分得好（10 段），AFM 是一整塊。
- 還有的問題：
  - 「低音原因 → 底層原因」改錯了，正確是「第一性原理」。雖然有標出修正，但改法本身是錯的。
  - 修正紀錄多了一筆「沒改」的無效項目。
  - 摘要最後一點「心流的條件同樣適用於規劃與設計」是推論，原文沒有。
- 結論：**錯字修正和幻覺控制都大幅勝過 AFM**，而且有標示，使用者能看出哪裡被改過。代價是逐字稿文字要上雲端、每 5 分鐘約 0.4 美分。

## 照稿念的真人錄音（script-01，2 分 16 秒，對 MacBook 麥克風直接講）

稿子是 `samples/script-01.ref.txt`，模擬團隊站會，約 530 字，中英夾雜。結果在 `out/s1/`。

| 引擎 | CER | 加 Haiku 修正後 | 辨識耗時 |
|---|---|---|---|
| SpeechAnalyzer（即時錄音當下） | 14.3% | — | 即時 |
| SpeechAnalyzer（錄完轉檔） | 12.9% | 8.6% | 1.9 秒 |
| whisper large-v3-turbo | 9.8% | 6.8% | 11 秒 |
| **Breeze ASR 25** | **3.3%** | **2.7%** | 23 秒 |

- CER 會把「14 天」和「十四天」這種數字寫法的差異也算成錯誤，所以 Breeze 實際的錯字比 3.3% 還少。
- Haiku 每次修正約 0.2 到 0.35 美分。

關鍵術語有沒有辨識對（SA = SpeechAnalyzer）：

| 術語 | SA | turbo | Breeze | Breeze + Haiku |
|---|---|---|---|---|
| deploy / callback / Cloudflare / Telegram | ❌ | ✅ | ✅ | ✅ |
| timeout / code review | ❌ | ❌ | ✅ | ✅ |
| Redis | ❌ | ❌ | ❌ radius | ✅ 依上下文修正 |
| Hyperf | ❌ | ❌ | ❌ HyPath | ❌ |
| cert-manager | ❌ | ❌ | ❌ Sir manager | ❌ |
| 儲值 / 有效投注 / 第一性原理 | ❌ | ✅ | ✅ | ✅ |
| 心流 | ✅ | ✅ | ✅ | ✅ |

結論：
- **Breeze ASR 25 明顯勝出**，字錯率約為 turbo 的三分之一、SpeechAnalyzer 的四分之一。之前那段 5 分鐘錄音出現的幻覺，這次沒有發生。
- **Haiku 修正在每個引擎上都有幫助**，但能修好的只有上下文推得出來的詞（radius → Redis、供單 → 工單）。Hyperf、cert-manager 這種專有名詞，沒有上下文線索就修不回來。下一步可以給 Haiku（或 whisper 的 `--prompt`）一份**詞彙表**。
- SpeechAnalyzer 即時錄音的結果（14.3%）比錄完轉檔（12.9%）稍差，只適合當錄音時的即時草稿。

## 會議記錄流程加速（2026-10-15）

一場 25 分半的演講（`recordings/2026-10-15_1330`），原本的流程從按停止到會議記錄完成要約 9 分鐘：Breeze f16 6 分半、Haiku 2 分半。改了四個地方：

| 改動 | 結果 |
|---|---|
| **邊錄邊轉**（`meeting.py`）：錄音程式在講者停頓、而且累積 20 秒以上時切出一段 16 kHz WAV，最長 60 秒一定切；`whisper-server` 讓模型常駐記憶體，每段一出現就辨識 | 60 秒測試：**停止後 7 秒逐字稿完成，16 秒會議記錄完成** |
| **Haiku 只回傳行號修正**，不重寫全文；修正由程式在本機套用，短句依 Haiku 給的段落邊界合併 | 25 分鐘的錄音：145 秒 → 51 秒，輸出 40K → 11K tokens，US$0.022 → 0.007 |
| **Breeze q8_0** | 只快約 20%（5 分鐘的錄音 60 → 47 秒），CER 3.3% → 3.5%。**模型小一半（1.66 GB）**，所以改成預設 |
| **VAD**（silero v5.1.2） | 靜音片段的幻覺（「(撮影時…)」「(音樂)」）消失了。預設門檻 0.5 會把小聲的話切掉，改成 `-vt 0.35 -vp 300`；但「大家好」仍然被切掉，而且長靜音之後第一句的時間戳會錯（顯示 0 秒，實際是 65 秒） |

- 詞彙表（`glossary.txt`）同時放進 whisper 的 prompt 和 Haiku 的 system prompt：script-01 修正後的 CER 從 2.7% 降到 **2.0%**，cert-manager 修對了，Hyperf 還是沒有（HyPath / iPath）。
- 錄音程式踩到的坑：分段檔先用 `.part` 副檔名寫入再改名，結果 AVAudioFile 依副檔名寫成了 CAF，whisper-server 讀不了。改成在 `tmp/` 底下直接用 `.wav` 寫，完成後再搬過去。

## App 的切段規則（segtest.py，2026-10-15）

可以重複執行的離線測試：用 script-01 組出一段 4 分 31 秒的音檔，結構是「65 秒環境雜音 → script-01 → 45 秒雜音 → 開頭 25 秒、音量降到 30% 的重播」，然後模擬錄音程式切段，比較三種做法：

| 做法 | CER | 整段雜音（00:00–01:00） | 講完後 45 秒的雜音 | 時間戳（正確是 01:09 / 04:10） |
|---|---|---|---|---|
| old：切 20 到 60 秒的段落，每段都開 whisper `--vad`（`meeting.py` 現在的做法） | 3.8% | ⚠️ **whisper-server 當掉** | 沒有幻覺 | 01:09 / 04:10 |
| new：同樣的切法，VAD 只用來略過整段無聲 | 41.6% | 略過 | ❌ **大量幻覺**（「一個的一個的…」「we are the world」「[音樂]」） | 01:00 / 04:04 |
| **gap**：依 VAD 的語音片段組成段落，**停頓超過 2 秒就切開並丟掉停頓**，開頭保留 1 秒、結尾保留 0.3 秒，最長 60 秒；送進 whisper 時不開 `--vad` | **3.8%** | 不會出現（沒有語音就不會產生段落） | 沒有幻覺 | **01:08 / 04:10** |

- **whisper-server 開 `--vad` 時，收到整段無聲的音檔會當掉**（VAD 判定沒有語音之後，接著判斷語言時出錯）。實際開會只要停頓超過 60 秒就會碰到，`meeting.py` 有這個問題。
- 「new」的幻覺證明：**送給 whisper 的音訊裡不能夾著長時間的雜音**。只略過整段無聲的段落還不夠。
- 「gap」的準確度和 old 一樣，又不會當掉，時間戳也正確，而且停頓 2 秒就送出一段，即時性比較好。小聲的重播也辨識得到。
- **開頭保留的時間要不對稱**：用真實錄音 `recordings/2026-10-15_1326.m4a` 測試（安靜一分多鐘後，廣播「大家好，這裡是 A 會議室…」），VAD 判斷的開口時間比實際晚，前後各留 0.3 秒時「大家好」會被切掉；降低 VAD 門檻（0.2）也救不回來。開頭改留 1 秒就找回來了。但如果結尾也留 1 秒，相鄰段落會重疊、同樣的字被辨識兩次，CER 從 3.8% 升到 5.7%。所以**開頭留 1 秒、結尾留 0.3 秒，而且開頭不能早於上一段的結尾**。
- **App 採用 gap 規則**：Rust 端對錄音串流持續跑 Silero VAD（whisper-rs 的 `WhisperVadContext`），停頓超過 2 秒、或段落長度達到 60 秒就送出一段（開頭留 1 秒、結尾留 0.3 秒、不重疊），whisper 本身不開 VAD。

## 分辨講者（單一麥克風，2026-10-16）

程式在 `spike/diar/`：`make_dialogue.py`、`make_real_mix.py` 產生測試資料（講者已知），`src/main.rs` 跑 sherpa-onnx 的完整流程，`src/bin/cluster.rs` 用 sherpa-onnx 的聲紋模型、搭配自己寫的分群，`score.py` 計分。模型（不進 git）：pyannote segmentation 3.0、3D-Speaker ERes2Net（中文訓練）、NeMo TitaNet small（英文訓練），都來自 sherpa-onnx 的 GitHub releases。

測試資料（都是 4 個人，約 85 秒）：
- **舊式合成**：Meijia、Eddy、Flo、Grandpa。後三個是同一套舊式引擎，音色很接近。
- **自然合成**：Meijia、Tingting、Sinji（三個都是女聲）加 Rocko。
- **真人拼接**：Rory（script-01）和三場演講的講者，各 6 段交錯。各自的麥克風和環境不同，所以會比真實會議（同一支麥克風）好分。

「每句正確率」：以每句話裡佔最多時間的講者為結果，算判斷正確的比例，最接近 App 一句逐字稿標一個講者的用法。

| 做法 | 舊式合成 | 自然合成 | 真人拼接 |
|---|---|---|---|
| sherpa-onnx 內建分群，指定 4 人 | 60%（只分出 3 人） | 55%（3 人） | 75%（3 人） |
| sherpa-onnx 內建分群，自動判斷（門檻 0.5） | 70%（5 人） | 70%（5 人） | 88%（8 人） |
| **sherpa 切段 + 3D-Speaker 聲紋 + 自己的分群，指定 4 人** | **100%** | **95%** | **100%** |
| **同上，自動判斷（門檻 0.55）** | **100%（4 人）** | **95%（4 人）** | **100%（4 人）** |

- **sherpa-onnx 內建的分群是瓶頸**，不是聲紋模型：同一個人的片段相似度平均 0.82 到 0.85，不同人只有 0.18 到 0.28（3D-Speaker，合成語音）；真人拼接是 0.66 對 0.07。指定人數時，內建分群在三組都只分出 3 個人，兩個聲紋模型的結果還完全一樣，看起來是它指定人數的做法有問題。
- 自己的分群：平均連結（average linkage）的餘弦相似度階層式分群，只用 1 秒以上的片段計算，更短的（「好」「對」）最後再歸給最相近的群。
- **中文聲紋模型比較好**：真人拼接時，TitaNet（英文）只有 79%，3D-Speaker（中文）100%。
- **門檻 0.55 到 0.6 三組都對**；真人組在 0.65 開始把同一個人拆開，0.5 以下會把聲音相近的人合併。預設用 0.55。
- **速度**：約 8 倍即時（1 小時約 7 到 8 分鐘），而且 90% 以上的時間花在 sherpa-onnx 內建流程重複計算聲紋。只用它的切段模型、聲紋自己算，應該能快很多。
- **還沒驗證**：真正的多人會議（同一支麥克風、有人搶話、講者聲音相近）。合成和拼接的資料都比真實情況好分。

### 真實會議（96 分鐘、同一支麥克風，「上週資安事件後續修補與本週需求討論」）

沒有正確答案，只能看講者切換是不是跟著問答走。

- **門檻 0.55 完全失效**：分出 361 群（sherpa 內建分群是 586 群）。真實會議的聲紋相似度整體偏低，沒有測試資料那種「同一人約 0.66、不同人約 0.07」的兩群分布，而是集中在 0.1 到 0.3、往高處拖尾。
- **改成只用 3 秒以上的片段、門檻 0.3**：主要分成 8 群左右，逐字稿看起來大致合理，問答通常會切到不同人（例如「有個問題／確認是發生在 QA 後還是 QA 前」→「QA 後」）。但也有明顯錯誤：開頭的「推了嗎」「沒有我最後已經推了」被分成同一個人，因為 sherpa 把連續的短句切成同一段。
- **門檻不能從測試資料直接搬過來**，要用標好答案的真實會議片段來調；人數可能也要讓使用者事後合併或改名。
- **速度不夠**：sherpa 切段 806 秒（7 倍即時）加分群約 3 分鐘，96 分鐘會議共要約 16 分鐘。

### 從會議裡建聲紋再認人（`src/bin/identify.rs`，2026-10-17）

| 留一句測一句（其他標註句建聲紋） | 45/45 = 100% |

## AFM 調校（2026-10-16，`AFM/main.swift` + `afm.py`）

目標：讓本機的 AFM 產出和 Haiku 同樣格式的會議記錄，看調校後能接近到什麼程度。測試資料：script-01（站會，有正確稿件）、`recordings/2026-10-15_1700`（24 分鐘演講，453 行）。

做法：每次請求只做一件事、只處理一段；長逐字稿依 AFM 自己的 tokenizer 切段（每段 ≤ context 的 1/4），分段整理重點後再合併；輸出用 DynamicGenerationSchema 結構化。

| 嘗試 | 結果 |
|---|---|
| 校對：給詞彙表，讓 AFM 自己找錯字 | script-01 **0 筆**（Haiku 4 筆），CER 3.3% 沒變 |
| 校對：程式找出和詞彙表拼字相近的候選（22 筆），AFM 回答是或否 | **22 筆全部答「否」**，包括 radius→Redis、Sir manager→cert-manager、供單→工單 |
| 校對：同上，改成 A/B 二選一、先寫一句分析 | 選 B 的 4 筆**全錯**（例如 效投注→總投注），真正的錯字仍全部選 A |
| → 結論 | **AFM 無法可靠地修正辨識錯誤**，校對步驟關掉（`AFM_VERIFY=1` 可重測），只保留程式做的大小寫修正 |
| 長逐字稿第一版 | 兩次結果差很多：一次 318 秒、一次 111 秒；**一次整份輸出英文**；兩次都把演講當成會議並編出 2 到 3 筆待辦；標題是所有主題串在一起；段落每 1 到 2 行就切；後半段內容遺漏 |
| 指示加「一律繁體中文」、標題 ≤ 25 字、段落改由程式依停頓切 | 語言、標題、段落都正常了 |
| 類型改成單獨一次請求（逐字稿開頭 1500 字，三選一） | 三場演講都判成 memo（個人口述），memo 允許待辦，所以還是編出待辦 |
| 加程式規則：判成 memo 但「大家/各位」≥ 5 次就改判 talk（演講 19 / 24 / 40 次，站會 2 次）；talk 由程式清空決議與待辦 | 演講判對、待辦清空；站會仍判 meeting、待辦「小明今天下班前 code review」正確 |
| 合併時主題上限 8 → 10 | 演講的 make verify 段落出現了，但最後的 PR template、CI 仍沒列到 |

最終結果和 Haiku 比較：

| | AFM（調校後） | Haiku 5.5 |
|---|---|---|
| script-01 CER | 3.3%（沒修任何錯字） | **2.0%** |
| 24 分鐘演講耗時 | 64 到 69 秒 | 33 秒 |
| 內容類型 | 靠程式規則才判對 | 判對 |
| 主題涵蓋 | 大致依序，最後 1 到 2 分鐘的內容會漏 | 開頭到結尾完整 |
| 術語 | 辨識錯的照抄（Rayleigh/Raymi = README、golden = golang、adrian = agent） | 修正 30 處 |
| 同一份輸入跑兩次 | 結果差異大（語言、耗時、主題） | 穩定 |
| 費用、隱私 | 免費、離線 | 約 US$0.005、逐字稿上雲端 |

- **適合的用途**：離線或資料不能上雲端時的備案，產出「大致正確、但錯字照抄」的會議記錄。
- **不適合**：需要修正辨識錯誤、需要穩定一致的結果。
- 調校手段的效果排序：程式規則（類型、段落、清空待辦）> 拆成單一任務 > 改 prompt。小模型做判斷題、校對題都不可靠，能用程式決定的事就不要交給它。

### 量測時踩到的坑

- PowerShell 5.1 的 `>` 轉導會在檔案開頭加 UTF-8 BOM，`cer.py` 靠 `^\[mm:ss\]` 擷取逐字稿，**第一行會被丟掉**（第一次 CER 4.5%，去掉 BOM 後 2.5%）。輸出要用 `Start-Process -RedirectStandardOutput` 或存成無 BOM。
- PowerShell 函式的參數不能取名 `$args`（內建自動變數），會變成空值。
