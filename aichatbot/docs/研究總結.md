# 專案總結：LINE AI 客服

> 最後更新：2026-10-08（新增：目前架構與檔案說明改成 Swift Package 版、greedy 的代價（第 13 節）；設計原則補充（第 4 節）、迴圈後續幾輪（第 11 節）、量測改用 greedy（第 13 節）、店家決定（第 14 節）；2026-10-06：挑 FAQ 改善實驗（第 12 節）、自動改進迴圈 `loop/`、驗證題組 `eval/holdout/`；之前：新版架構 `bot.swift`、完整流程題庫、分類改善實驗、案例庫）

## 目標

開發一個 LINE AI 客服，參考了 YouTube 影片〈我做了一款免費軟體！Mac 內建 AI 直接打造 LINE AI 客服，零 API 零費用〉（頻道：I'm 阿湯）介紹的「顧店」LINE AI 客服：
一個 Mac App，用 macOS 內建的 Apple AI 模型當 LINE 官方帳號客服，功能包含知識庫、待補問題、回覆規則、轉接專人、禁止主題、預約收單與日曆檢視。

訊息流程：LINE 官方帳號 → Cloudflare Tunnel → 自己的 Mac → Apple 本機 AI 回覆。

---

## 主要發現

### 1. 開發環境

- 開發機：Apple M4、16 GB、macOS 27。
- 預設模型就是 **AFM 3 Core Advanced**（Apple 最強的本機模型），上下文上限 **8192 token**。
  - 較舊或較弱的 Apple 裝置會使用一般的 AFM 3 Core，品質可能更差。正式 App 應在啟動時檢查 `SystemLanguageModel.default.variant`。
- **Apple 私有雲模型（Private Cloud Compute）**：上下文 32768 token，但需要 Apple 核發的 entitlement（`com.apple.developer.private-cloud-compute`），並且要用 Xcode 建立、簽署的 App 才能呼叫。短期內無法使用。
- 目前只裝了 Command Line Tools，沒有 Xcode，所以 `@Generable` 巨集無法使用（測試時改用 `DynamicGenerationSchema`）。正式開發需要安裝 Xcode。

| 類別 | 第 1 輪 | 第 2 輪 |
|---|---|---|

| 地址、付款外送、包場 | 全對 | 全對 |
| 價格菜單 | 9/10 | 10/10 |
| **計算與條件** | 5/12 | 6/12 |
| 資料沒有 | 9/10 | 7/10 |
| **模糊沒脈絡** | 3/6 | 0/6 |
| 刁難 | 8/8 | 7/8 |
| 錯字口語 | 5/6 | 5/6 |
| 英文 | 4/6 | 5/6 |
| 日文 | 3/5 | 4/5 |
| **總計** | **70/88（80%）** | **68/88（77%）** |

另外：意圖分類 75/80（94%），平均每次回答約 1.3 秒。

| 擅長 | 不擅長 |
|---|---|
| 意圖分類、從選項中挑選 | 計算與條件判斷（自己打折、算錯總價、門檻判斷錯誤） |
| 抽取資料（姓名、日期、電話、人數） | 模糊、無脈絡的問題（常編出回答或列出整份菜單） |
| 依資料回答基本問題 | 憑空捏造（例如編出不存在的「大杯 180 元」） |
| 不洩漏系統提示 | 分不清對話中的「你、我」 |
| 速度快、免費、資料不離開電腦 | 同一題每次結果不一定相同 |

其他觀察：

- 正確回答「週一公休」時，卻把狀態標成「資料沒有」，流程會因此改成轉店員（尚未修正）。
- 會自行承諾「我們會盡快回覆」等沒做過的事（已加入輸出檢查攔截）。
- 保留對話紀錄時會一直抄自己上一句（已改成每題重新開始）。
- 兩個 AI 呼叫同時執行時，回答品質明顯變差（已改成依序執行）。
- 韓文、越南文等語言的回答品質差，已決定**只支援中、英、日**，其他語言回固定的多語說明並轉店員。

### 4. 設計原則（由測試歸納）

| 原則 | 原因 |
|---|---|
| **AI 只做選擇題** | 分類、挑 FAQ、抽欄位很準；自由回答容易亂編 |
| **規則與計算交給程式** | 本機模型和 Haiku 都會算錯門檻與折扣 |
| **防護關卡只能往安全方向改** | AI 審核員失敗：擋掉正確答案、放過亂編的回答 |
| **程式關卡為主，AI 關卡要先量準確度** | 每多一個 AI 關卡，錯誤率就疊加一次 |
| **AI 呼叫一次只跑一個** | 本機模型同時跑多個會出錯 |
| **對話紀錄要短，或每題重新開始** | 小模型會抄自己前一句 |
| **抽出的資料必須能在原文找到** | 防止模型編造名字、人數、日期 |
| **語言先看文字系統，再交給語言辨識** | 「可以用LINE Pay嗎」曾被誤判成英文 |
| **短句語言判斷偏向支援的語言** | 「Hi, I am Kevin」曾被判成 80% 印尼文 |
| **預約問欄位時，短答不切換語言** | 中文預約問到姓名回「Bill」，之後都變成英文（#17） |
| **用固定題庫驗證每次修改** | 避免「修好一個、弄壞另一個」 |
| **AI 呼叫全部用 greedy 取樣** | 同一句話每次結果相同（不穩定題數 7～9 → 0）。AI 只做選擇題、不寫回覆，所以不必依環節調 temperature；回覆的變化交給 `replies.json` 的多種說法隨機挑 |
| **先抄原文出處，再判斷** | 欄位依序產生：先選答案再抄出處時，AI 會先猜（例如「自取」）再找一段原文湊數；先抄再選就不會（取貨方式、挑 FAQ 都這樣做） |
| **出處和值要一致** | 出處抄對「25 個人」、值卻填 10（取自日期 10/21）；出處有數字時，值必須是其中之一，不一致就當沒抓到、再問一次 |
| **數字欄位用整數型別** | 文字欄位曾填出「{10}」「)」；guided generation 的整數型別只能輸出數字 |
| **新判斷拆成獨立的 AI 呼叫，不要往既有 schema 加欄位** | 讀訂單多一個欄位，「各一杯」「100 塊」就讀錯；同一個 schema 的欄位會互相影響 |
| **不用關鍵字清單判斷語意** | 多語系會漏（「我自己過去拿」「swing by and grab」）、也會誤判（take ⊂ mistake）；要確認 AI 沒亂猜就用原文出處 |
| **給 AI 的指示寫成陳述句** | 指示寫成問句時，AI 把指示本身抄成原文出處 |
| **比對原文時忽略標點和空白** | AI 抄日文時把「？」寫成「?」 |

### 5. 評估過的方案

| 方案 | 結論 |
|---|---|
| Dify、n8n、Flowise | 不建議：接 Apple 模型要靠社群轉接程式，會失去強制格式輸出；約 8 個容器，很吃資源；授權禁止多租戶 SaaS |
| LangChain、LangGraph、NeMo Guardrails、Parlant、Rasa | 不直接引入；借用概念（AI 只理解、流程由程式控制；規則寫成資料） |
| Instructor、Outlines | 不需要：Apple 已內建強制格式輸出 |
| promptfoo | 值得考慮：用於回歸測試、A/B 比較 |
| AnyLanguageModel（Hugging Face） | 值得考慮：與 Foundation Models 相同寫法，可切換到 Claude、Ollama 等（尚未 1.0） |
| Linux 部署 | Apple 模型只能在 Apple 裝置執行；改用 Linux 就得換成雲端或開源模型 |
| Ollama 本機開源模型（7～9B） | Mac 或 RTX 3060 12GB 都跑得動，品質預期優於 Apple 模型，**尚未實測** |
| 微調模型 | Apple 模型的 Adapter 在 macOS 27 SDK 已標示 `obsoleted`，無法微調；改用「案例庫」（見第 9 節） |

### 6. 舊版 `chat.swift` 的問題（重新設計的原因）

`chat.swift` 是「遇到一個錯就加一層過濾」累積出來的，review 後發現：

| 問題 | 說明 |
|---|---|
| 沒有明確的對話狀態 | 靠比對上一句回覆的文字判斷「是不是在等店員」，追問邏輯改了三次仍不穩 |
| 補丁式的 AI 是非題 | 追問、「我想一下」、名字各加一個 AI 判斷，每則訊息最多呼叫 6 次 AI，錯誤率疊加 |
| 測試工具混進產品邏輯 | A/B 並排的結果被拿來判斷追問，狀態又依 A 的回覆追蹤 |
| 補丁沒有量測 | 多數只憑一兩個手動例子加入，不知道拿掉會變好還是變差 |

完整流程題庫上，`chat.swift` 平均只有 **65%**。

### 7. 新版架構 `bot.swift`

| 設計 | 內容 |
|---|---|
| 明確的狀態 | `Customer`：名字、語言、預約問到哪個欄位、有沒有事在等店員、追問次數、連續無關次數、是否轉人工 |
| 一次分類 | 每則訊息一次 AI 選擇題（13 類＋「看不懂」），同一次呼叫順便抽名字；分類時附上目前狀態與案例庫的相似例子 |
| 依表分派 | 程式依「狀態 × 意圖」決定怎麼回（模板、預約流程、FAQ、轉店員、轉人工） |
| AI 不自由寫回覆 | 店家問題用 FAQ 答案；價格由程式依 `store.json` 計算；挑不到 FAQ 才轉店員 |
| 規則寫成資料 | `store.json`（菜單、價格、折扣、營業時間、人數上限）、`replies.json`（中英日固定回覆）、`faq.txt`、`examples.jsonl` |
| AI 呼叫 | 一般訊息 1 次；店家問題 2 次；算價格、預約、轉店員前確認各再 1 次；一律依序執行 |
| 除錯 | `BOT_DEBUG=1` 印出每一步的 AI 判斷 |

程式規則（不靠 AI）：
- 語言：先看文字系統，再交給語言辨識；只支援中英日。預約問欄位時的短答（名字、電話）不切換語言（「Bill」曾讓中文預約後面都變成英文）。
- 只有表情、標點 → 閒聊。
- 極短訊息（1～2 個字、純英文 3 個字母以內）不當成店家問題或預約，改請顧客說清楚（預約中不套用）。
- 名字：必須出現在原文、不能是整句話、問身分或追問等句子不抽名字、單一個字只在明確自我介紹時採用。
- 預約欄位：要有原文出處或數字依據；剛問的欄位直接採用；姓名必須有文字（電話曾被收成姓名）。
- 預約日期、時間：AI 填整數的月日時分，要和出處的數字一致；「明天」「下週二」這類相對說法由程式依今天換算（`RelativeDate.swift`），AI 填的月日不用。AI 自己算曾把週三說的「下週二」算成週六，出處沒有數字所以沒被擋下（#16）。換算不了的說法（下下週、週末）不填，改問日期；AI 漏抄成「下週三」時，出處和原句裡的「下下週」重疊也不填。明確寫出的月日（10/19、10月19日）由程式從出處或原句讀出來，AI 填的月日不用（AI 曾把「10/19」的月日填成 0，明確日期被丟掉，F13 退步）；寫了好幾個日期時，AI 填的要是其中之一。日期和時間的出處彼此重疊（「10/19 下午兩點」）不算重疊，時間比對數字時不看日期的數字。
- 轉店員前先確認顧客真的在發問，避免「好」「我想一下」變成待處理事項。

### 8. 分類改善實驗（`intent_set.json`，102 句 × 2 輪）

| 方法 | 分類準確度 | 結論 |
|---|---|---|
| 原本的寫法 | 74% | 27 個錯有 24 個被分成「店家問題」 |
| 加入「看不懂」類別 | 72% | 沒用：例句寫在說明裡也照樣分錯 |
| 店家問題移到最後 | 77% | 錯誤改跑到排第一的「預約」→ **確認小模型不確定時會挑第一個選項** |
| 「看不懂」放第一個 | 72% | 所有不確定的都變成「看不懂」，連「好」「Hello!」都是 |
| 先用一句話描述顧客想做什麼，再選類別 | 76% | 誤分成店家問題的次數減半（有害錯誤變少） |
| 兩階段（先粗分 5 類再細分） | 72% | 更差，而且多一次 AI 呼叫，已移除 |
| ＋極短訊息規則 | 79% | 精準但涵蓋範圍小 |
| ＋案例庫（中文為主，93 個） | 89% | 閒聊、身分、看不懂、自我介紹大幅進步 |
| **＋案例庫補英日文（169 個）** | **91%** | 自我介紹 12/12，不穩定題數從 13 降到 2 |

結論：**改提示詞的寫法到 75% 左右就到頂了；要突破得給 AI 新的資訊（相似句子的正確答案），而不是換一種問法。**

### 9. 案例庫（`examples.jsonl`）

- 「這句話 → 正確意圖」的已標記例子，169 個（中文 72、英文 57、日文 40），部分附上對話狀態（等店員時、預約中問某欄位時）。
- 運作方式：
  - 跟案例完全相同（而且狀態相同）→ 直接沿用標籤，不呼叫 AI。
  - 否則用 Apple 內建的上下文語意向量找出最相似的 6 個例子，附在分類提示詞裡給 AI 參考。（Go 版改用多語言句子向量，見第 15 節。）
- 語意向量本身不夠準（實測 6 句只對 4 句、分數差距小），所以不單靠相似度做決定，而是交給 AI 參考。
- **案例不能和任何測試題重複**，否則分數只是「背答案」；目前用程式檢查過沒有重複。
- 之後的維護方式：店員看到判錯的句子，標上正確答案加進案例庫，`/reload` 立即生效。

仍會造成問題的情況：
- ~~挑 FAQ 挑錯：「有停車位嗎」→「自取打 9 折」~~（已改善，見第 12 節）；「有大杯嗎」「可以去冰半糖嗎」仍會回菜單。

### 11. 自動改進迴圈（`loop/`，詳見 `loop/README.md`）

把「改一點 → 跑題組比分數 → 變好才留」自動化（改用 greedy 後每題只跑 1 次，見第 13 節）：

| 步驟 | 誰做 |
|---|---|
| 讀紀錄與失敗明細、提出一個假設、做最小修改 | AI（`claude -p`，指令在 `loop/PROGRAM.md`） |
| 檢查只改允許的檔案、FAQ 答案沒變、沒寫死測試句、案例不重複 | 程式（`loop/gate.py`） |
| 開發＋驗證題組評分、決定保留（git commit）或還原 | 程式 |
| 記錄結果與心得給下一輪 | `loop/LEDGER.md`、`loop/NOTES.md` |

- 新增**驗證題組**（`eval/holdout/`：流程 8 段 26 步、分類 41 句，加上 `faq_set.json` 原有的 15 題 holdout）。AI 只看得到總分，用來抓「只對開發題組有效」的修改。
- 保留條件（2026-10-07 起）：開發綜合分數 +0.2 以上，或程式變短且持平，或**答錯少 2 題以上且開發分數沒降**；答錯不能增加；驗證分數最多掉 3.0。（改用 greedy 前是 +1.0、答錯少 3 次、答錯最多多 1 次。）被還原的修改存成 `loop/runs/<時間>/rejected.patch`。
- 守門程式只管 `eval/` 和 `Sources/`：曾把使用者自己在改的 `docs/TODO.md` 還原掉、把專案根目錄的未追蹤檔案搬走，已修正。

### 13. 量測方式改成 greedy（2026-10-07）

改之前每題要跑 2～3 輪取平均：118 題中有 9 題時對時錯，3 輪平均的標準差約 ±0.75 次／輪，差 2 次以上才算真的變化；剩下的答錯常在 0～4 次之間跳動，接連兩個和它們無關的修改被「答錯 +3」擋下。

- `ask()` 加上 `GenerationOptions(sampling: .greedy)`：分類、單題各跑 3 輪，不穩定題數都是 0；兩次獨立執行，六個題組的分數和失敗明細逐題相同。
- 量測改成每題 1 次：一次完整評分約 21 分鐘 → 9.5 分鐘（拆成 Swift Package 後含編譯約 13 分鐘）。
- 門檻依「一題值多少分」重算：開發綜合分數是三個題組百分比的平均，修好 1 題約 +0.28（單題 118 題）～+0.43（流程 77 步）。門檻 0.2 = 至少淨修好 1 題，並擋下「修好一題、改壞另一題」的交換（+0.05～+0.15）。題庫變大時要重算。
- 參考過「客服不同環節用不同 temperature」的建議（分類 0、知識庫回答 0.2～0.4、閒聊 0.5）：那是給讓 AI 自己寫回覆的系統用的；這裡 AI 不寫回覆，所以全部用 greedy。
- 注意：greedy 只保證同一個模型版本結果相同，macOS 更新模型後要重量基準；結果固定後題庫更容易被「背」，驗證題組更重要。
- greedy 的代價：①錯誤從「偶爾錯」變成「每次錯」，顧客重傳同一句也一樣錯，要換說法才行；②看不到「不穩定」這個訊號（模型舉棋不定的邊緣題，最值得補案例），需要時可暫時改回隨機取樣跑一次診斷；③提示詞改一點點，不相關的題目就可能翻轉，迴圈可能保留「剛好翻對」的修改，靠驗證題組和 +0.2 門檻擋。
- **同時有兩個程式呼叫本機模型仍會失真**（呼叫變慢、超過 15 秒逾時就落到預設值），greedy 解決不了。→ 已由 #7 解決：AI 呼叫經跨程序檔案鎖排隊，等鎖不算進逾時，同時跑只會變慢。

### 15. 技術驗證：Go 的多語言語意向量（#23，2026-10-09）

Go 版不能用 Apple 的 `NLContextualEmbedding`，改用開源的多語言句子向量：hugot v0.7.0＋`intfloat/multilingual-e5-small`（ONNX 版）。程式在 `go/internal/embed`（載入、算向量），`go/cmd/embed`（先算好向量檔給 Swift 版讀），`go/cmd/xlang`（跨語言抽查）。做法：句子前面加 `query: `，mean pooling（有看 attention mask），再做 L2 正規化。

- 6 補的案例（`eval/examples.jsonl` 最後 14 句，`check_overlap.py` 無重複；檔案照舊用 Swift 版的代號 `store_question`、`small_talk`，Go 版讀進來合併成 general）：問包場規則→general（包場最低消費多少、包場時段可以待幾個小時、Can we rent the whole shop for a party?）、語助詞→general（等一下喔、嗯哼）、要客服扮演別人→identity（現在換你當客人、我們來角色扮演，你演老闆、Let's switch roles, you are the customer now）、日文自我介紹→self_intro（初めまして、木村と申します）、罵人→complaint（你好蠢、笨死了、這什麼鬼回答）、指代不明→unclear（那是誰、哪個）。都是題目的同類句，不是題目本身；但「那是誰／他是誰」「哪個／這個」「嗯哼／嗯嗯」「等一下喔／等等」「你好蠢／你很笨欸」「現在換你當客人／從現在起你是顧客」和題目很接近，量驗證題組時要特別看這幾類。
- 6 不開快取（`BOT_AI_CACHE=0`）重跑一次也是 97/101，答錯同樣 4 題：好了沒（沒有狀態）→general、回答什麼東西啊→unclear、還有嗎→general、他是誰→identity。想找真人 4/4，沒有「AI 失敗」。
- 流程題（F09 F10 F12–F15 F18 F24–F33，真模型 1 次）：**47/50 步**（門檻 43）。沒過的 3 步都在預約：F13（週一公休）、F14（人數上限）是 Go 版預約本來就不檢查公休日、人數（#26）；F32 預約完成時時間記成 18:00（應為 19:00），分類對了，是預約抽欄位的問題。#27 合併時同一組也是 47/50。
- 沒有動分類提示詞，「分類提示詞有洩題」（TODO）這次沒有處理。

**結論**

- e5 的分數擠在一起，改挑案例的規則（同意圖上限、短案例、相對門檻）和 K 都只在 −3～+1 題之間擺動（K=4 量測無效，不算），看不出方向，不採用；`similar.go` 維持取前 K 句。
- 有效的是補意圖案例：答錯的題目大多是案例庫缺那一類句子（包場規則、角色扮演、日文「と申します」、罵笨），補同類句後前幾名就換成對的意圖。
- 最後設定：K=6（不變），挑案例規則不變，案例庫 196 → 210 句。剩下的 4 題錯有 3 題（好了沒、回答什麼東西啊、他是誰）也是 Swift 版 Apple 向量在第 15 節答錯的。第 15 節的 95/101 是舊的 14 類標記；#26 依 11 個意圖重新標記後，「10 類換算」把閒聊、問商家等合併成 general，Swift 版是 97/101，這次的目標就是這個數字。
- 只靠一份 101 題的開發題組調案例有過度擬合的風險，要看驗證題組（由人量，不能低於 37/41）。

## 目前架構

> 2026-10-08 起改成 Go 服務＋Vben 後台、AI 讀知識庫寫回覆（見 [`開發計畫.md`](開發計畫.md)、[`docs/adr/`](adr/)）。下面是 Swift 版（tag `swift-final`）的架構，研究結果仍然適用。

```
Telegram（之後接 LINE，平台層抽一層）
 → Cloudflare Tunnel → 這台 Mac 的 webhook 伺服器（Hummingbird 2）
 → 程式：語言辨識、表情符號、極短訊息
 → 本機 AI（一次選擇題，greedy）：意圖分類＋抽名字，參考案例庫        ← 免費
 → 程式：依「狀態 × 意圖」分派
      固定回覆／預約流程與驗證／追問升級／轉人工
 → 店家問題：AI 挑 FAQ，價格由程式計算，挑不到才轉店員
 → 顧客狀態、對話紀錄存 SQLite（GRDB），伺服器重開可以接續
 → 回覆
```

- 第一版純本機模型；AI 呼叫抽成一層（`ChatModel`），之後換 Claude Haiku 或 Ollama 時用同一套題庫量過再決定（見 [`開發計畫.md`](開發計畫.md)）。
- 所有 AI 呼叫經跨程序檔案鎖排隊，同一台 Mac 上的多個程式也不會同時呼叫本機模型。
- 還沒做：LINE 串接、店員端（Telegram 群組）、管理介面。

## 檔案說明

### 程式（Swift Package，`swift build -c release`）

| 位置 | 用途 |
|---|---|
| `Sources/BotCore/` | **客服核心**（「訊息進、動作出」）：對話狀態（`State`）、意圖分類（`Intent`）、店家問題與價格計算（`StoreQuestion`）、預約（`Booking`、`RelativeDate`）、模型層與排隊（`Model`、`AI`、`AIQueue`）、設定與固定回覆（`Config`） |
| `Sources/Storage/` | SQLite 資料庫（GRDB）：顧客狀態、已處理的 update、對話紀錄 |
| `Sources/Telegram/` | Telegram 平台層：webhook、Telegram API、設定 |
| `Sources/server/` | 執行檔 `server`：Telegram webhook 伺服器（環境變數見 `.env.example`） |
| `Sources/bot/` | 執行檔 `bot`：終端機對話，以及各題組的量測模式（`BOT_INTENT_EVAL`、`BOT_TESTSET`、`FLOW_TRACE`） |
| `Tests/bot-tests/` | 對話層測試（用照腳本回答的假模型，不需要本機模型）：`swift build && .build/debug/bot-tests` |
| `Tests/telegram-tests/` | webhook 層測試（假 Telegram API）：`swift build && .build/debug/telegram-tests` |
| `data/bot.sqlite` | 伺服器的資料庫 |
| `loop/` | 自動改進迴圈（見第 11 節與 `loop/README.md`） |
